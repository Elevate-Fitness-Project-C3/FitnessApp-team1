`Fitness_Profile_Service/` (namespaces use `FitnessProfileService`).

## Configuration

The ID-06 auth stack is reused unchanged through `BuildingBlocks/FitnessApp.Auth`.

- `Jwt:Issuer`, `Jwt:Audience` — set in `appsettings.json`.
- `Jwt:SigningKey` — **never checked in**. Supply via user-secrets or `Jwt__SigningKey`
  environment variable (minimum 32 characters).
- `ConnectionStrings:DefaultConnection` — supply via user-secrets or
  `ConnectionStrings__DefaultConnection` environment variable.

Local user-secrets example (values not shown here):

```powershell
dotnet user-secrets set 'Jwt:SigningKey' '<at-least-32-chars>' --project Fitness_Profile_Service/FitnessProfileService.csproj
dotnet user-secrets set 'ConnectionStrings:DefaultConnection' '<sql-connection-string>' --project Fitness_Profile_Service/FitnessProfileService.csproj
```

In Development the initial EF migration is applied automatically at startup.

## Endpoints

All endpoints require a valid JWT. Ownership always comes from the token's `sub` claim;
there is no user id in any route.

| Method | Path | Auth | Success | Failure |
| --- | --- | --- | --- | --- |
| POST | `/api/profile/onboarding` | Any authenticated user | `201` | `400` validation, `401` no/bad token, `409` already onboarded |
| GET | `/api/profile/me` | Authenticated + onboarding gate | `200` | `401`, `404` no profile, `409` onboarding incomplete |
| GET | `/api/profile/me/measurements` | Authenticated + onboarding gate | `200` | `401`, `409` onboarding incomplete |
| POST | `/api/profile/me/measurements` | Authenticated + onboarding gate | `201` | `400` validation, `401`, `409` onboarding incomplete |
| GET | `/api/profile/dev-check` | Authenticated | `200` | `401` |
| GET | `/openapi/v1.json` | Anonymous in Development | `200` | — |

Onboarding validation rules: age 15–100, height 100–250 cm, weight 30–300 kg, at most one
decimal place, training experience ≤ 30 chars, available days 1–7. Rejected requests never
write to the database.

For the wider auth contract (401 for missing/invalid/expired token, 403 for wrong role,
404 for another user's resource in services that expose id routes), see the shared auth
library and TrainingService. This service intentionally exposes only `/me` routes, so a
different user's token simply cannot reach another user's data.

## Development token

The temporary token endpoint in IdentityService is only mapped in Development:

```powershell
# POST http://localhost:5190/api/dev/token
{ "userId": "00000000-0000-0000-0000-000000000001", "role": "User" }
```

It is marked for removal once ID-03 login exists. The Docker IdentityService runs in
Production and does not expose it; use the local Development host for these checks.

## Verify

```powershell
dotnet build FitnessApp-team1.slnx
dotnet test FitnessApp-team1.slnx --no-build
```

Runtime smoke check (with both local hosts running):

```powershell
dotnet run --launch-profile http   # in IdentityService/  -> :5190
dotnet run --launch-profile http   # in Fitness_Profile_Service/ -> :5069
```

Observed results: openapi `200`, no token `401`, invalid token `401`, before onboarding
`409`, onboarding `201`, after onboarding `200`, measurements `200/201`, duplicate onboarding
`409`, invalid onboarding `400`.

Regenerate the migration if the model changes:

```powershell
dotnet ef migrations add <Name> --project Fitness_Profile_Service/FitnessProfileService.csproj --startup-project Fitness_Profile_Service/FitnessProfileService.csproj --output-dir Infrastructure/Persistence/Migrations
```
